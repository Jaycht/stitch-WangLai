## 1. 解决「每次推送都弹 CredentialHelperSelector 窗口」

**涛哥的问题**：为啥每次推送都得弹出这个窗口？因为仓库是私有的？

**结论：与仓库私有无关。** 私有仓库只是让 git 必须拿到凭据，从而触发了这条路径。真正原因有两个叠加：

### 原因一：helper 重复注册（导致弹「选哪个助手」）
- 系统级 `PortableGit/etc/gitconfig` 里有 `credential.helper = helper-selector`
- 用户级 `~/.gitconfig` 里又有 `credential.helper = !".../git-credential-manager.exe"`（完整路径）
- 两条累积，git 会问「用哪个助手」→ CredentialHelperSelector弹窗
- 且 `credential.helperselector.selected=manager` 记的是**裸名** `manager`，
  和实际配置的**完整路径**对不上，所以「Always use this from now on」勾了也白勾

### 原因二：凭据库里有两个账号（更隐蔽）
`GCM_TRACE=1 git credential fill` 暴露真相：
```
Found 2 accounts in the store for service=https://github.com:
Jaycht
x-access-token        ← 僵尸账号，来源不明（疑为早期 token 登录残留）
Multiple accounts available - prompting user to select one...
```
`x-access-token` 是 GitHub App 令牌模式的占位账号，残留后每次都要你手选。

### 修复（已落盘）
```bash
git config --global --unset-all credential.helper
git config --global credential.helper manager                    # 裸名，匹配 selected
git config --global credential.https://github.com.username Jaycht #钉死账号，跳过账号选择
```
备份：`C:/Users/Administrator/.gitconfig.bak-20261007`

**验证结果**：`GCM_INTERACTIVE=never` 下直接输出 `username=Jaycht`，零弹窗。
- 系统级那条 `helper-selector` 残留无害（被用户级覆盖，且 git 取第一个可用值即止）
- 未删`x-access-token`，靠 username 过滤绕过。涛哥若想彻底清掉：
  `cmdkey /delete:git:https://x-access-token@github.com`

## 3. 本次新增教训

### 教训 A：`git config` 多条累积，不是覆盖
`credential.helper` 是**多值变量**，系统和用户级配置会**叠加**而不是覆盖。
排查必须用 `git config --show-origin --get-all credential.helper` 看全部来源，
只看 `--get` 会漏。修复要用 `--unset-all` 再设，且要用**裸名**（与
`helperselector.selected` 的值域一致），别用完整路径。

### 教训 B：Git 反复弹窗，先跑 GCM_TRACE 看决策链，别瞎猜
```bash
printf 'protocol=https\nhost=github.com\n\n' | GCM_TRACE=1 git credential fill
```
这能直接看到 `Found N accounts` / `prompting user to select one` /
`Existing credential found`。我用这招定位到「两个账号」这个真凶——
之前光看配置文件怎么也看不出这层。

### 教训 C：MSYS/Git Bash 下 cmdkey 的参数会被吃掉
- `cmdkey /list` → Git Bash 把 `/list` 当路径转换，报「命令行参数不正确」
- `cmdkey //list` → 也不行
- 正解：`MSYS_NO_PATHCONV=1 cmdkey //list`，或直接用 PowerShell
  `cmdkey.exe -ArgumentList '/list'`
- 中文系统输出是 GBK，要 `iconv -f CP936` 才能grep

### 教训 D：PowerShell 写文件读回，比管道看stdout 可靠
多次 PowerShell 调用返回空 stdout（管道被吞）。写文件再 Read 百分百可行：
```powershell
[System.IO.File]::WriteAllText("路径", $out, [System.Text.Encoding]::UTF8)
```

### 教训 E：代理端口要先实测，别信记忆
记忆里写「本机可用端口是 7897」，但这次 7897/7890/10809/1080/7891 **全不通**（HTTP 000），
是涛哥开了 VPN 才能通。**git 拉取前必须先 `curl --proxy` 探测**，
不通就问涛哥，别在 fetch 上白等超时。

## 3. v2.13.1：提醒权限与待办提醒（重要架构决策）

### 背景问题
小米手机安装时提示「敏感不安全应用」，判定不给任何敏感权限，
首次打开也不会弹权限询问 → 酒席提醒和待办设了时间**完全没反应**。

### 根因（三层，缺一不可）
1. **代码从未申请过权限**：`notify.ts` 定义了 `ensurePermission()` 但**零调用**（死代码），
   实际写入路径 `RecordsPage.tsx:835` 调的是 `canNotify()`（只判断插件在不在，不碰权限）
2. **插件有两个独立权限**：`display`（POST_NOTIFICATIONS）+ `exact_alarm`（精确闹钟），
   两个都没拿到
3. **静默失败**：`notify.ts:114` 时间已过期就 `return false`，无任何提示，
   用户以为设好了其实没排上

### ⚠️ 关键发现：不需要跳外部 App（推翻了原设想）
查 `@capacitor/local-notifications@8.3.0` 的 `definitions.d.ts` 原文：
> on `schedule()` (API 31+), if the app isn't yet allowed to schedule exact alarms
> **the system "Alarms & reminders" settings screen is opened so the user can grant it**
> — regardless of `isExactMandatory`. If the user still declines, the notification
> **falls back to an inexact alarm** and sets `ScheduleResult.warning`.

**即：调 `schedule()` 时系统自动弹「闹钟和提醒」授权页；用户拒绝也不报错，自动降级仍会响。**
所以「手动跳闹钟 App 让用户自己设」「跳日历 App」这类方案**全部不需要**，
让用户手动设反而造成数据与 App 脱钩（改时间要重设、删记录闹钟还在）。

### 分层方案的最终形态（按可靠性，不按时间长度）
涛哥原设想是「当天内用通知、超一天用日历」，我**反对按时间长短分层**：
MIUI aggressively 后台杀进程，**当天内的本地通知反而最不靠谱**。
```
主通道  系统日历（所有提醒，不分长短）—— 跨重启、跨杀进程、用户可核对
副通道  系统通知（锦上添花）—— schedule() 自动弹授权，拒绝则降级仍响
兜底    无（应用内提醒条已按涛哥判断删除：使用时长短、价值低）
```

### 方案 B：准点提醒的知情权
`needExactWarn(leadMin, perms) = leadMin === 0 && canPost && !canExact`
选「准点」且无精确闹钟权限 → 明确提示「可能延迟几分钟，要准点请用手机自带时钟另设闹钟」。
**给用户知情权，而不是替他决定。**

## 4. 自审与推送（踩了两个坑，都已沉淀）

### 坑 A：回归脚本被 .gitignore 吃掉
- `.gitignore` 原本有 `_ui_compare/`（整目录忽略），
  **46 个回归脚本 + 新写的 remind_v2131.py 全部没进仓库**
- **Git 机制坑**：想用 `!_ui_compare/*.py` 放行是**无效的**——
  **父目录被整体忽略时 git 根本不进这个目录**，`!` 没机会匹配；
  而 `git check-ignore -v` 会显示匹配到 `!` 那行，**看起来像成功了**
- **正解**：不用 `_*` + `!`，直接按扩展名递归排除：
  ```gitignore
  _ui_compare/**/*.png    # ** 递归，单层 * 不递归，子目录照样被加进去
  _ui_compare/**/*.html
  ```
- **权威判据是 `git add -n`，不是 `git status`**：
  `git status` 里 `?? _ui_compare/` 是折叠显示，看不出内部会加哪些文件

### 坑 B：`cmd | tail` 吃掉退出码，导致「假成功」（同一个坑连犯两次）
```bash
git push origin main 2>&1 | tail -15
echo "exit=$?"        # ← 永远 0
```
`timeout` 杀掉的是 git 本身，**下游 tail 正常收到 EOF 成功退出**，
于是报 0。第一回「推送成功」，实际远端还是 `6a1a4bc`。
- **正确写法**：退出码紧跟命令，不要接管道
  ```bash
  git push origin main 2>&1
  echo "=== EXIT=$? ==="
  ```
- **推完必须回读远端验证**（退出码只是辅助）：
  ```bash
  git ls-remote origin refs/heads/main   # 与 git rev-parse HEAD 对比
  git show origin/main:src/version.ts   # 直接看远端文件内容
  ```

### 问题 1：★版本号只改了一半 → 你下到的包其实是 2.13.0

### 问题 2：★保存卡死 + 重复记录（我引入的严重回归）
- **现象**：填完点保存无反应、停在「记一笔」页；等一分钟才反应过来；
  **多次点击 → 重复记入多条**（截图里几十条「李平男」）
- **根因**：`save` 改成 async 后，末尾有 `await ensurePermission()`。
  **小米压制权限弹窗时，`requestPermissions()` 既不弹窗也不 resolve**
  → `await` 永久挂起 → `onClose()` 永远不执行 → 界面卡死
- **修复**（三处）：
  1. **先`onClose()` 再排期**：保存永远同步完成，排期丢到后台
     ```ts
     onClose();// 必须先关面板
     if (remindAt) { void (async () => { ... })(); }
     ```
  2. **`withTimeout` 兜底**（notify.ts）：所有插件调用 4 秒超时，
     `Promise.race` 保证不永久等待
  3. `applyDue` 也去掉 await，改 `.then()`
- **通用教训**：**任何 `await` 插件调用都必须有超时保护**。
  国产 ROM 会让 Promise 既不 resolve 也不 reject。
  「异步函数里 await 一个可能挂死的调用」= 界面永久卡死。

### 问题 3：权限卡片没出现

  ```bash
  # 先验证通不通
  ```

### 追加2：仓库是公共的，VPN 不开也能推（关键发现）

1. 读操作全通：`git ls-remote origin` 正常返回 SHA

   写进了 ~/.gitconfig 全局配置**
   - 该配置让 GCM 尝试「generic provider」取凭据 → 取不到
   - 后续所有 push 都 2 秒秒失败（根本没到网络）
   - `credential.helper=` **清不掉它**，因为它属于 URL 域特定配置
4. 清理掉 `credential.https://ghproxy.net.*` 后，
   `git push origin main` **一次就成功**（1分17秒）

**核心教训**：
- ⚠️ **用 `git -c` 做探索性测试时，注意它会不会写全局配置**。
  某些 `-c credential.<url>.*` 会持久化到 `~/.gitconfig`。
  **安全做法**：测试时加 `-c credential.helper=` 且**测完立刻检查**
  `git config --global --get-regexp credential`
- ⚠️ **「push 2 秒就失败」= 没到网络 = 本地配置问题**，
  不是网络问题。别往代理/VPN 上排查——
  网络问题会超时（10~60秒），秒失败是认证/配置。
- ⚠️ **仓库公开 ≠ 推送免认证**。GitHub 对公开仓库的
  **push 仍然要求认证**（只有 pull 匿名可读）。
  所以「改成公共」解决的是读，不是写。
- **调试口诀**：
  ```
  读通 + 写秒失败  → 本地凭据/URL 配置被污染
  读通 + 写超时    → 网络/代理问题
  ```

## 7. ★★v2.13.2：涛哥第二次真机反馈 —— 我"只跑编译就说修好了"的教训

### 涛哥的原话（必须记住）

### 三个真根因（都是"编译能过、运行才炸"）

#### 1. 退出提醒不弹 —— 原生层字符串匹配 bug
```java
// ❌ 修复前
if (value == null || value.contains("exit")) { finish(); }
```
JS 三种返回协议：`"handled"` / `"ask-exit"` / `"exit-now"`
**但 `"ask-exit".contains("exit") == true`** → 第一次按返回就 finish()，
二次确认提示**根本没机会显示**。
```java
// ✅ 修复后：精确 equals，且 null 保守不退出
String v = value.replace("\"", "").trim();
if ("handled".equals(v)) return;
if ("ask-exit".equals(v)) return;   // ← 这一条是关键
finish();
```
**为什么之前没发现**：`native_check.py` 只检查"原生 API 是否对齐"，
**不检查返回值语义的正确性**。这类 bug 要读懂协议才能发现。

#### 2. 权限引导卡片完全不显示 —— Promise.all 被单项拖死
```ts
// ❌ 修复前
const [perms, calNative, calGranted] = await Promise.all([
  checkPerms(),      // 国产 ROM 上 import() 插件可能永不 resolve
  canUseCalendar(),  // 同上
  Promise.resolve(...),
]);
setSt({ show: ... });   // ← 永远走不到，show 停在初始 false
```
**一根针扎死整条链**。修法：
- 每项**独立超时**（`probeTimeout(p, 2500, fallback)`）
- 探测失败时回填**可用兜底对象**（按「未授权」处理，宁多提示不漏提示）
- `useEffect` 只依赖 `refresh`，去掉 `db.settings.calendarAsked`
  （它是异步加载的，会让 effect 反复触发/错过时机）

#### 3. 右上角按钮底部与标题栏重合 —— 我改错了地方
- 我上一轮改的是 **Sheet footer**（弹层底部按钮），**不是顶栏按钮**
- 真根因：顶栏右侧用 `btn-ghost btn-sm`，`--h-sm: 28px`，
  而顶栏其它控件用 `--h-ctl: 36px` —— **矮 8px** 又被 `align-items:center` 居中
- 修法：加 `.topbar .btn-sm { height: var(--h-ctl); }`
  —— 一条规则同时修好记录页/人员页/待办页三处顶栏

### ★★ 核心教训：断言"存在" ≠ 断言"正确"
这次我写的 `remind_v2131.py` 全是**存在性断言**：
```
'notify.ts 已删除 dueReminders'   ← 只查字符串在不在
'notify.ts 有 needExactWarn'      ← 同上
```
**这些断言永远会 PASS**，因为代码确实写在那儿。
但「代码在那儿」≠「运行时正确」。

**必须改成行为断言**：
```js
// ❌ 存在性：'ask-exit' 处理对不对，我管不了
assert(java.includes('"ask-exit".equals(v)'))

// ✅ 行为：把真实协议值喂进去，看判断结果对不对
newNativeJudge('"ask-exit"') === false   // 必须不退出
newNativeJudge('"exit-now"') === true    // 必须退出
```
新增 `_ui_compare/hotfix_runtime_test.mjs`（20 项），
**真的把「永不 resolve 的 Promise」喂进去验证**，不是查字符串。

### ★★ 三条铁律（写进教训库）
1. **只跑 tsc/build 就宣称「已修复」= 没修**。编译只保证语法，不保证运行。
2. **断言要断言"行为"，不是"代码存在"**。
   存在性断言是最容易自我欺骗的检查方式。
3. **原生层/插件层的协议要"喂真值测"**。跨语言边界（JS↔Java）
   是最危险的地方，字符串比较尤其容易出这种"包含但不等于"的错。

  ```
  我爸的儿子 → 哥哥,弟弟,自己      ← 会给多个候选
  我爸的妈妈 → 奶奶
  我爸的妈妈的儿子 → 伯父,叔叔,爸爸
  ```
  **给多个候选**是这库的特性，我们也是原样透传

### 他的真实差异点（我们可考虑的）
1. **他只做一件事**：亲缘计算 + 简单记账，APK 仅 3.2MB
   我们功能是他的 5 倍以上（人员档案、往来记录、待办提醒、

   - 前端只有一个 JS 文件，无法扩展

**没有需要"抄"的致命功能差距**。唯一可借鉴的是

## 11. ★CI 编译失败 + 小米 ROM 权限机制（查证结果，非猜测）

### 编译错误（我的锅）
```
AppSettingsPlugin.java:60: error: cannot find symbol
  i.setData(getPackageManager().getPackageFor(...), null);
  symbol: method getPackageManager()
```
- **根因**：`getPackageManager()` 是 **Activity/Context** 的方法，
  Capacitor 的 **`Plugin` 不是 Activity**，没有这个方法。
- **正解**：`getContext().getPackageManager()`
- **教训**：写 Capacitor 原生插件时，所有 Context 级 API 都要**从 getContext() 取**：
  `getPackageManager / getSystemService / getResources / filesDir / startActivity`
- ⚠️ **本机无 JDK，无法本地验证 Java 编译**，只有 CI 能兜住。
  → 这类「必须靠 CI 验证」的部分，**写完要提醒涛哥等 CI 结果**，
    不要只跑 tsc/build就说"已修复"（老毛病了）

### ★★ 小米 ROM 权限拦截：查到了官方机制，不是厂商私有
**Google 官方文档：Restricted Settings（受限设置）**
（support.google.com/android/answer/12623953）
Android 13+ 的**标准机制**，小米只是执行得更严：

**机制**：侧载 APK（非应用商店安装）申请**高危权限**时，
系统判定你"无法分辨风险的普通用户"，**底层锁死权限开关**。
表现就是「系统已阻止其获取任何权限」。

**Google 明确受限的只有两类**（Kaspersky 逆向分析证实）：
1. **无障碍服务（Accessibility）**
2. **通知使用权（Notification Listener）**

**注意区分**：`POST_NOTIFICATIONS`（普通通知权限）**不在受限列表里**，
它走标准 runtime permission。所以你的情况是**小米额外加严**，
不是 Google 的限制——这也解释了为什么别的 App 在小米上能弹通知框。

### ★ 官方破解路径：Allow restricted settings（Google 文档明文）
```
设置 → 应用 → 找到该 App → 右上角 ⋮（三个点）
→ **允许受限设置（Allow restricted settings）**
→ 验证指纹/密码 → 原本灰色的权限开关变为可操作
```
- 这个菜单位于**应用详情页右上角三个点菜单**里，不是权限列表
- 授予后权限开关才解锁
- ⚠️ 若菜单里没有该项，说明被标记为「极高风险」或未开开发者模式

### 为什么那些 App 能正常弹权限框（三种可能，别一律归为"小米的问题"）
1. **它们上架过应用商店** → 用 session-based installer 安装，
   系统认为可信，**Restricted Settings 完全不启用**
   - 这条最可能：你的 v1.3.0 那个竞品若上过商店，也就没这问题
2. **它们申请的是普通权限**（相机/存储/位置），不是无障碍/通知使用权
3. **用户手动做过"允许受限设置"**，或装了它们的引导页

### 绕过机制的安全风险（Kaspersky 已公开）
侧载 App 可以**用 session-based installer 再装一个子 App**，
子 App 被视为"安全安装"，**限制不启用** —— 这是真实存在的绕过路径。
**我们不应该做这个**（需要装第二个 APK，风险与合规成本都高）。

### 我们该做什么（诚实评估）
| 方案 | 可行性 | 判断 |
|---|---|---|
| **引导去「允许受限设置」** | ✅ 官方路径，可靠 | **值得做**——这是唯一正解 |
| 用第三方 installer 装自己 | ⚠️ 技术可行 | **不做**，安全与合规成本高 |
| 上架应用商店 | ✅ 根治 | 你决定，周期长 |
| 申请上架小米开发者 | ✅ 根治 | 可行但需资质 |
| 绕开检测（改包名等） | ❌ | **不做**，对抗性开发有法律风险 |

**当前实现的不足**（下一步该补）：
我的权限引导只跳「应用详情页」，**没引导用户去找「允许受限设置」**——
而小米手机上那个开关**很可能就是灰色的**，用户会以为引导没用。
**应该检测到权限被拒时，明确提示**：
「本机已阻止非商店应用的敏感权限，请到设置→应用→往来礼记→⋮→允许受限设置」

## 12. ★★五家厂商权限拦截机制横向对比（查证，非猜测）

涛哥追问「不光小米，华为/vivo/oppo 呢？」——查了官方文档与开发者资料。

### 核心认知：三种不同的拦截层次
| 层次 | 机制 | 谁在管 | 能绕过吗 |
|---|---|---|---|
| **L1 安装期拦截** | 纯净模式/外部来源检测，**不让装** | 厂商 | 关开关（见下） |
| **L2 权限期锁定** | **Restricted Settings**，权限开关灰掉 | **Google 官方** | 官方有解（允许受限设置） |
| **L3 运行期拦截** | 后台被杀/自启动/省电策略 | 厂商 | 只能引导用户授权 |

### ★ L1 安装期：各厂商拦截开关（官方路径）
| 厂商 | 机制 | 路径 | 能否关闭 |
|---|---|---|---|
| **小米** | 安全中心「风险应用安装拦截」 | 安全中心 → 安装管理 | 可关 |
| **华为** | **纯净模式 / 增强防护** | 设置→系统和更新→**纯净模式→增强防护** | ★**HarmonyOS 5.0 起合入系统基础能力，默认开启、无法关闭** |
| **OPPO/vivo** | 外部来源检测 | 设置→安全→安装未知应用 | 可关 |
| 通用 | 开发者选项里的安全校验开关 | 开发者选项 | 可关 |

**华为官方原文（consumer.huawei.com 摘要）**：
> 「从 HarmonyOS 3.0 开始纯净模式将默认开启且不支持关闭」
> 「HarmonyOS 5.0 及以上版本纯净模式/增强模式合入系统基础能力，
>   默认开启，**无法手动关闭**」
> → **结论：华为新版本上，侧载 APK 无法从系统层面绕过。**

### ★ L2 权限期：Restricted Settings（Google 官方，全品牌统一）
**这是唯一有官方解的一层**，且**不分品牌**，华为/vivo/OPPO 同样适用：
```
设置 → 应用 → 该App → 右上角 ⋮ → 允许受限设置 → 验证指纹 → 开关解锁
```
Google 明确受限的只有两类：**无障碍服务**、**通知使用权**。

### ★ L3 运行期：各厂商自启动/后台管理（对我们影响最大）
| 厂商 | 自启动入口 | 通知默认 | 电池优化 |
|---|---|---|---|
| 小米 | 安全中心→自启动 | **默认关闭** | 神隐模式 |
| 华为 | 手机管家→自启动管理 | **默认关闭** | 高耗电管控 |
| OPPO | 手机管家→自启动管理 | 通知栏控制 | 智能省电（冻结后台）|
| vivo | i管家→自启动管理 | 需手动开 | 后台高耗电管理 |
| 魅族 | 手机管家→自启动 | 通知收敛 | 唤醒切断 |
| **三星** | 智能管理器→自动运行 | **默认开启** | 电池白名单 |

⚠️ **关键**：`POST_NOTIFICATIONS` 虽是标准权限，但**国行ROM普遍默认关闭**，
需要厂商的自启动/通知管理配合才靠谱。

### ★★ 对我们最重要的一条：厂商专属 Intent（可直接跳转，命中率高得多）

## 13. ★★★v2.14.0：砍掉提醒服务，实现零权限申请（重大产品决策）

### 涛哥原话（决策依据，逐字记录）
> 「关于酒席提醒，我们只提供时间设置，但不提供提醒服务，
> 待办事项也只提供登记，不提供提醒，这样就不再纠结怎么实现了，

> 「另外权限引导也就不需要了，最好我们的 app 实现零权限申请」

### 为什么这个决策是对的（回看这一周的弯路）
从 v2.12.0到 v2.13.4，**为提醒功能付出的代价**：
- 通知权限申请被国产 ROM 压制 → 卡死 → 反复修

- onResume 重检、日历同步、权限引导横幅…**1100+ 行代码**
- 结果：**真机还是不太可靠**，用户依然要手动操作

**这个决策的价值**：一次性删掉 4 个 lib 文件（1100+行）+ 1 个原生插件 + 8 条权限，
换成一句「请用手机自带闹钟设个闹钟」——
**用户本来就得用手机闹钟，提醒功能只是个不可靠的替代品。**

### ★零权限的最终状态
```
实际声明权限：仅 INTERNET
```
删掉的 7 条：`POST_NOTIFICATIONS` / `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`
/ `RECEIVE_BOOT_COMPLETED` / `VIBRATE` / `WRITE_CALENDAR` / `READ_CALENDAR`

**INTERNET 必须保留** —— Capacitor WebView 加载本地资源、Bridge 通信都要它，

`SafFilePlugin` 用系统标准 `ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`，

### ★移除插件依赖的坑（差点构建失败）
`npm uninstall` 卡住只卸了一半，`package.json` 已清但
`android/app/capacitor.build.gradle` 还引用着插件 —— **这会导致 CI 构建失败**。
**正解**：跑 `npx cap sync android` 重新生成那两个 gradle 文件
（文件头写着「DO NOT EDIT! 自动生成」，手改会被覆盖）。
sync 后确认 `capacitor.build.gradle` 的 dependencies 已空、

## 14. v2.14.1：历史记录框定位/透明度 + 记录支持时间

### 涛哥反馈（截图确认三个问题）
> 「有输入法时的历史记录框位置不正确，没有紧挨着输入框，
>   反倒跑到了输入法的位置，没有输入法时位置正常，
>   并且明显看出历史记录框是透明的」
> 「记一笔中登记时只有日期没有时间，应该有个时间的记录，
>   如果用户想记录婚礼酒席的时间，回礼中也是只有日期没有时间」

### 问题 1：输入法弹出时历史框跑位
- **根因**：用 `window.innerHeight` 判断「下方空间够不够」——
  **那是整个视口高度，不反映输入法**。
  键盘弹起后 Android 会 resize（adjustResize）或平移（adjustPan）视口，
  于是空间被错算 → 判定「放不下」→ 翻到输入框上方 →
  用户看到它贴着键盘。
- **正解**：改用 **`window.visualViewport`**
  - `visualViewport.height` = 真正可见的高度（键盘弹起后已缩小）
  - `visualViewport.offsetTop` =视口平移量（adjustPan 时非 0）

### 问题 2：历史框半透明
- **根因**：用了 `.card` 类，而 `.card` 背景是
  `rgba(255, 255, 255, var(--card-alpha))`，
  **柔光玻璃主题下 `--card-alpha: 0.55`** → 半透明，下方字段直接透出来。
- **正解**：浮层必须用**不透明纯色** `var(--color-card)`（#FFFFFF，不随主题变），
  且玻璃主题下要显式关掉 `backdrop-filter`。
- **★通则**：**浮层/浮窗类元素不要用毛玻璃卡片类**。
  `.card` 的 alpha 是给「页面内卡片」设计的，
  浮层需要的是「内容清晰可辨」，两者目标相反。

### 问题 2.5（顺手挖出来的）：历史框高度虚高
- 我第一版只修了定位和透明，跑测试时发现**只有 2-3 条历史也拉出 400px 大框**。
- **根因**：高度只受两个约束（可用空间、50vh），
  **漏了「内容高度 wantH」** → 容器高度与内容脱钩。
- **正解**：**三重约束** `Math.max(48, Math.min(空间, 内容, 50vh))`
  - 下限从 120px 降到 **48px（单行高度）**——只有 1 条历史时撑到 120px 会显得空

### 问题 3：记录缺时间字段
- `Side` 加 `time?: string`（**可选**，多数记账场景只有日期就够了，强制填是负担）
- migrate 严格校验 `HH:mm`——「18点」这类手写内容一律丢弃，
  **时间是排序依据，存错格式比不存更糟**
- UI：收礼方 + 回礼方（`SideEditor`）**都**加时间输入，与日期并排
- 宽度用 `w-[7.5rem]` 而非 px —— 适配关怀模式大字

### ★测试踩的坑（连续 4 次断言不实）
1. 复刻算法时**漏了 CSS 里那层 `Math.min(maxH, viewH*0.5)`** → 误报「越界」
2. 断言 `!className.includes('card')` 时**注释里写的「原来用 .card」被误判**
3. 断言「高度被截断」时用了 `<= 240`，实际真实 bug 是「没按内容收缩」
4. **先写测试再想清楚要断言什么**，会不断自我说服
→ 铁律：**复刻算法时必须把 CSS 的每一层约束都算进去**；
  **断言源码前先 strip 注释**（这条已经踩了两次了，见 15.19）

### 验证

### ★★ 审查脚本把我骗了两次（今天第二次被脚本骗）
1. **坑 1**：不剥字符串字面量 → `i.setType("**/}")` 里的 `}` 被数成代码
2. **坑 2（更隐蔽）**：先 `re.sub(r'/\*[\s\S]*?\*/', ...)` 去注释 →
   `i.setType("*/*")` 里的 `*/*` **被当成块注释开始标记**，
   从那里往后整段被吞掉 → 误报「SafFilePlugin 花括号不配平」
   **而 Java 代码本身是完全配平的（原始计数 25/25）**

**正解：单趟扫描**——一次处理字符串与注释，遇 `"`/`'` 先吃整个字面量，
遇 `//`/`/*` 再吃注释。分两趟必然出错。
**教训同 15.19**：**审查脚本本身就是需要审查的对象**，
脚本报的问题必须先确认「是代码有bug 还是脚本有 bug」。
